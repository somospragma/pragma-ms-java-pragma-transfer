# HU-03 · Pagar a un celular PragBank (evolución con SDD)

**Como** cliente de PragBank **quiero** buscar a otro cliente por su número de celular, ver su nombre enmascarado y enviarle hasta S/ 500 **para** pagar cosas del día a día sin pedir números de cuenta.

Repos: `pragma-ms-java-pragma-transfer` (código) y `pragma-iac-tf-pragma-transfer` (tabla nueva). Contrato: `openapi/ms-transfers-v3.yaml`. Integra `openapi/alias-directory.yaml`. Reglas: RN-09 a RN-13 (ver abajo y [docs/business-rules.md](../business-rules.md)) y, de la v1, RN-03 y RN-05 a RN-08.

Se entrega con el ciclo SDD: spec → plan → tareas.

## Alcance

- **Dos endpoints nuevos en el micro:** `GET /api/v1/phone-transfers/recipients` y `POST /api/v1/phone-transfers`. Igual que en la v1, requieren `X-Customer-Id`; la API key la valida API Gateway. Cada ruta lleva su `@RouterOperation` para aparecer en el Swagger.
- **API Gateway:** el recurso `/{proxy+}` reenvía cualquier ruta al micro, así que los endpoints nuevos quedan expuestos con solo desplegarlo.
- Tabla DynamoDB `recipient-tokens`: llave `recipientToken` (S), TTL en `expiresAt` (5 minutos). El uso único se garantiza con una escritura condicional sobre `usedAt`.
- El pago reusa el flujo de la v1 (débito, crédito, compensación y eventos) con `channel = PHONE`.
- Nueva dependencia: directorio de alias, con `DIRECTORY_BASE_URL` (en dev `http://mocks:8080`, por Service Connect).
- Library del micro: agregar `DYNAMODB_TABLE_RECIPIENT_TOKENS`, `DIRECTORY_BASE_URL` y el secreto `DIRECTORY_API_KEY`. El pipeline escribe la llave en `SECRET_APIS_NAME` y el micro la lee de ahí al arrancar.

## Reglas de negocio

| Regla | Qué valida | Si no se cumple |
| --- | --- | --- |
| **RN-09** | Celular con formato `+51` + 9 dígitos que empiezan en 9 | 400 `PHONE_INVALID` |
| **RN-10** | El celular está afiliado en el directorio de alias y es de PragBank | 404 `RECIPIENT_NOT_FOUND` · 422 `RECIPIENT_NOT_SUPPORTED` |
| **RN-11** | Pago a celular de máximo S/ 500.00 y solo en `PEN` | 422 `LIMIT_PER_TX_EXCEEDED` |
| **RN-12** | El `recipientToken` existe, es del mismo cliente, está vigente (5 minutos) y no se ha usado (un solo uso) | 422 `RECIPIENT_TOKEN_EXPIRED` |
| **RN-13** | El destinatario no es el mismo cliente (cuenta destino igual a la origen o del mismo `customerId` en el core) | 422 `SELF_TRANSFER` |

De la v1 se reusan: RN-03 (monto), RN-05 (acumulado diario), RN-06 (saldo), RN-07 (antifraude) y RN-08 (idempotencia).

**Orden de evaluación del pago:** forma y RN-03 → RN-08 → RN-12 → cuenta origen del cliente (403) → RN-13 → RN-11 → uso único del token → flujo de la v1 con `channel = PHONE` (RN-04, RN-05, RN-01, RN-02, RN-07, RN-06 y SAGA). Los rechazos anteriores al uso único no consumen el token, no guardan transferencia ni publican evento.

## Directorio de alias (ya está mockeado)

Los stubs están en `mocks/mappings/directory-*.json` y corren en el mismo WireMock (local y en dev):

| Celular | Respuesta del directorio | Para probar |
| --- | --- | --- |
| `+51987654321` | PragBank, Mario Quiroz, cuenta `191-0007654321` | Pago exitoso y `maskedName` |
| `+51999111222` | PragBank, cuenta origen `191-0001234567` (cliente `CUST-000123`) | `SELF_TRANSFER` |
| `+51912345678` | Otro banco | `RECIPIENT_NOT_SUPPORTED` |
| Cualquier otro | 404 | `RECIPIENT_NOT_FOUND` |

Para pagar con un cliente nuevo (sin el acumulado diario de otras pruebas) se usa una cuenta comodín `191-8` + 9 dígitos con el cliente `CUST-` + la cuenta; ver `mocks/README.md`.

## Prerequisitos de la máquina

Los mismos de la HU-01, más Kiro con el flujo SDD (spec → plan → tareas). Prueba previa:

```bash
./gradlew build
docker run --rm -p 9090:8080 -v $PWD/mocks:/home/wiremock wiremock/wiremock:3.9.1
# en otra terminal
curl -s http://localhost:9090/directory/v1/aliases/+51987654321
```

Fuera de alcance: celulares de otros bancos (interoperabilidad).

```gherkin
Escenario: celular de un cliente PragBank
  Dado que +51987654321 está afiliado a la cuenta PragBank de Mario Quiroz
  Cuando busco +51987654321
  Entonces recibo 200 con maskedName Mar*** Qui*** y un recipientToken
  Y la respuesta no incluye el número de cuenta

  Cuando busco 987654321 sin prefijo, un celular no afiliado o uno de otro banco
  Entonces recibo 400 PHONE_INVALID, 404 RECIPIENT_NOT_FOUND o 422 RECIPIENT_NOT_SUPPORTED

Escenario: pago exitoso
  Dado que obtuve un recipientToken para +51987654321 hace 1 minuto
  Cuando pago S/ 45.50 con ese token
  Entonces recibo 201 con status COMPLETED y channel PHONE
  Y targetPhoneMasked es +51 9** *** 321

Escenario: token vencido o ya usado
  Dado que el recipientToken tiene más de 5 minutos o ya se usó
  Cuando pago con ese token
  Entonces recibo 422 con code RECIPIENT_TOKEN_EXPIRED
  Y no se hace ningún débito en el core

Escenario: TTL de DynamoDB aún no borró el token
  Dado un token vencido que todavía existe en la tabla
  Cuando pago con ese token
  Entonces el micro lo rechaza por expiresAt, sin depender del borrado del TTL

  Cuando pago con un token de mi propio celular
  Entonces recibo 422 con code SELF_TRANSFER

Escenario: excede el límite o no es en soles
  Cuando pago S/ 500.01 o US$ 20.00
  Entonces recibo 422 con code LIMIT_PER_TX_EXCEEDED

Escenario: entregado con SDD
  Entonces el repo tiene specs/003-phone-transfer con spec.md, plan.md y tasks.md
  Y cada tarea cerró con su prueba en verde
```
